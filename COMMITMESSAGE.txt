refactor(viz): remove the one dataset-specific palette from the package

amyloevo is a general package, and it had one study's group names written into
its code in four places that actually ran:

    src/amyloevo/viz/itol.py
        GROUP_PALETTE = colour_for(["FXR1", "FMR1", "FXR2",
        "pre-duplication"]) -- module level, and exported in __all__

    workflow/scripts/itol_annotations.py
        palette.get("FXR1", "#D55E00") -- three times, picking the accent
        colour for the block-presence, gradient and bar tracks

GROUP_PALETTE was never read by any function in the package: only exported and
asserted in tests. palette_for() already serves every caller by computing the
palette from the groups it is handed, so the constant was convenience with a
dataset baked in. Removed, with a test asserting it stays removed -- a
convenience constant is exactly the kind of thing that creeps back.

The three lookups in the workflow script become ACCENT, the head of the shared
Okabe-Ito cycle. That is a correction and not just a rename: those three
tracks carry block presence and mean block occupancy, which are quantities
rather than groups, so painting them in one paralogue's colour invites the
reader to think the track is about that paralogue.

The tests that pinned hex values to FXR1/FMR1/FXR2 now use Alpha/Beta/Gamma/
Delta. What they verify is that palette_for delegates to viz.groups.colour_for
-- not that one dataset comes out a particular colour, which is a fact about
the dataset and belongs with it.

Swept for what else ran on those names: nothing. config/config.yaml still
carries reference.value "9606", which is a configured setting with a
documented default and the right place for a dataset specific.

NOT changed here: sixteen modules still cite the FMR1/FXR1/FXR2 family in
docstrings, as the worked example a constant was chosen against. No code
branches on any of it. Whether that prose should be genericised is a separate
decision and a separate commit.

348 tests pass.
